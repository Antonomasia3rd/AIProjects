# Gmail and Google Workspace Mail tiles

Create **Tiles > Add tile > Mail / Gmail**, then use **Source settings > Google account for this Mail tile...**. Import the publisher/user's own Google Cloud **Desktop app** OAuth JSON, enable the Gmail API in that Cloud project, and choose **Connect to Google**. Authorization happens in the normal browser. DesktopStub does not collect a Google password, inspect browser cookies or reuse a Calendar grant. Disconnect removes this tile's local grant without changing any email or revoking unrelated applications.

The initial **Headers** setting requests `gmail.metadata` and retrieves sender, subject, Inbox unread counters and the authenticated mailbox address. **Snippet** is an explicit option requiring a new connection with `gmail.readonly`. Google does not allow full message format under metadata scope; Snippet therefore uses the read-only full format with a partial-response field selection restricted to identity/date, snippet and headers. Bodies, MIME parts, attachments, avatars and remote images are not requested. Source: [Gmail response formats](https://developers.google.com/workspace/gmail/api/reference/rest/v1/Format), [partial responses](https://developers.google.com/workspace/gmail/api/guides/performance#partial_response) and [Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes).

These account permissions are separate from Calendar permissions. The Windows-user-protected credential envelope also binds its purpose, profile, tile and OAuth client. Changing Headers/Snippet requires reconnecting; an incompatible saved credential fails before any Gmail request. A public distribution must meet Google's applicable OAuth verification requirements; the setup does not bundle another application's client ID or bypass Google's consent policy.

Each `Tile.<id>` uses its own `Mail.ClientId`, `ClientSecret`, `RefreshTokenProtected`, `Preview`, `UnreadOnly`, `MaxMessages`, `RefreshSeconds`, `TimeoutSeconds`, `MaximumBytes`, `PrimaryField`, `SecondaryField` and `BadgeEnabled`. The default is unread Inbox messages, three rows, headers only, a 120-second refresh, a 15-second per-request timeout and a 2 MiB aggregate inbox-response budget. The source supports at most five rows and one shared 45-second fetch deadline. The same options use the ordinary INI, generic CLI `--set`, tray and Properties surfaces. No Mail source is active merely because the program supports the type.

Inbox filtering uses `labelIds=INBOX` and optionally `UNREAD`; it does not use Gmail's unsupported metadata-scope search parameter. The numeric unread message/thread counts come from the Inbox label's explicit counters, rather than the approximate message-list estimate. An additional bounded profile read supplies the mailbox address in memory for the current account's browser activation; it is not a tile text field or credential log. Source: [message listing](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list), [Inbox label data](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.labels/get) and [account metadata](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users/getProfile).

Sender, subject and snippet remain separate source values. The default presentation deliberately chooses sender as primary and subject plus any permitted snippet as secondary; both choices are configurable. This is a Gmail presentation choice, not a claim that the installed Windows Mail producer used those exact semantics. The shared layout plan follows the [verified installed Mail builder](native-mail-tile-evidence-2026-10-25.md): Medium wraps two lines for each field, Wide allows one primary/three secondary lines, and Large aggregates regular caption pairs with two secondary lines. Small retains static artwork. Explicit typography and branding remain effective. Numeric badge publication is separate from the text plan and can be disabled per tile.

The prepared display projection caps sender at 256 characters and subject/snippet at 512 each, without changing raw provider fields or cutting a UTF-16 surrogate pair. Five unusually long multibyte message rows therefore still fit the actual 64 KiB UTF-8 notification transport bound.

The optional numeric badge uses private version-three transport metadata only when requested; existing raw/version-one/version-two payloads remain unchanged. Windows updates the badge after the tile content succeeds. A badge-only failure is reported separately and cannot trigger another successful queue's reset/retry. Zero clears the badge; Windows displays values above 99 as 99+. This transport applies to native packaged tile delivery, and its live platform acceptance remains separate from the injected fixture. Source: [Windows badge schema](https://learn.microsoft.com/en-us/uwp/schemas/tiles/badgeschema/element-badge).

The source uses fixed HTTPS endpoints, disables redirects, bounds response bytes and rejects partial/malformed results. Refreshes run on the existing asynchronous source worker with a memory-only access-token cache. A transient failed refresh can retain the previous good view with a separate stale diagnostic. Changing account/configuration or disconnecting drops that cached content, and a result from an older revision cannot replace current data.
