# Wuthering Waves Real-Time Notes

DesktopStub's WuWa provider reads the **overseas Wuthering Waves launcher** role data. It uses an explicitly supplied **game access token**, obtains a launcher OAuth code, optionally discovers roles, and queries the selected role. It does not read another application's files, browser cookies, game memory, or passwords. It does not log the token, OAuth code, raw request, response, or remote error message.

This is an unofficial integration with Kuro's service. The protocol was checked against [Wuthery/kuro.py](https://github.com/Wuthery/kuro.py) commit `4be620b2fbdc05eb2e2b6bb3aba68ae348d27c22` on 2026-10-23. No upstream Python implementation is bundled. Kuro can change or withdraw these endpoints, expire a token, reject an SDK session, or require additional authentication. No actual Kuro account was contacted during validation.

## Account setup

Create a Wuthering Waves tile and use its **Sign in** action. Enter the Kuro email/password for the overseas game account, complete human verification if requested, choose the linked character/server, and select **Save selected account**. Google/Apple-only sign-in is not implemented in this dialog. Sign-in starts only when the user presses its button; no account login runs at program startup.

The window starts at approximately 300 pixels high. It opens the larger verification area only after the current challenge's navigation has succeeded **and** GeeTest reports readiness through the session's nonce-bound page message, then collapses again when that challenge finishes or fails. An initial blank document cannot expand the window. Script/runtime failures and the 30-second load deadline have an explicit **Retry verification** action; the normal sign-in path reserves no empty browser panel. The supported minimum width keeps the sign-in, retry, save and close controls separate while resizing.

Password login, game-token exchange, launcher authorization and character lookup are separate stages. A `1005` character-lookup response happens after the preceding authorization stages succeeded; the inspected upstream wrapper treats it as retryable, but it does not document the server-side cause. DesktopStub reports the stage and numeric code without displaying remote messages or credentials. If lookup remains unavailable, **Retry character lookup** reuses the temporary authenticated token and does not ask for the password again. It does not automatically save an account without a selected character. The temporary session expires after five minutes or is discarded on Close; a persistent service-side failure still needs a later successful retry or an updated unofficial protocol.

The native sign-in dialog follows the upstream [email/password and authorization-code exchange](https://github.com/Wuthery/kuro.py/blob/4be620b2fbdc05eb2e2b6bb3aba68ae348d27c22/kuro/client/components/auth/subclients/game.py). Both requests use fixed HTTPS endpoints with POST form bodies and disabled redirects. The SDK's password wire encoding is Base64 plus shuffling; it is **not encryption**, so TLS remains essential. The implementation never puts a password in a URL, INI, log, notification, or CAPTCHA document. Temporary input/request buffers are cleared after completion or cancellation; the password remains in memory only while the active sign-in or its human verification needs it.

When Kuro returns the verification-required status, DesktopStub displays the verified [GeeTest game challenge](https://github.com/Wuthery/kuro.py/blob/4be620b2fbdc05eb2e2b6bb3aba68ae348d27c22/kuro/client/components/auth/client.py) in an isolated, mandatory InPrivate WebView2 session. The user solves it manually. Only the challenge proof returns to the native dialog, guarded by its origin, random nonce, request lifetime, and five-minute deadline. The browser receives no account email, password, or game token. Closing the dialog cancels its worker and discards unsaved inputs; program shutdown joins outstanding workers before teardown.

Only the game access token is retained after explicit role selection, always protected with Windows DPAPI for the current user. Saving checks that the active profile, tile type and account configuration still match the dialog's original target. The generated device ID is saved with the selected role, so later refreshes use the same explicit session identity.

Advanced users can still enter the **overseas game access token** directly in that tile's account settings. This is the `access_token` returned by the SDK's `get_game_token` flow; it is **not** a HoYoLAB cookie, a KuroBBS web token, an OAuth code, or a gacha record URL. See the upstream [game tests](https://github.com/Wuthery/kuro.py/blob/4be620b2fbdc05eb2e2b6bb3aba68ae348d27c22/tests/client/components/test_game.py) for the protocol sequence.

Leave player ID and region empty to discover the account's roles. If exactly one matching role is found, the provider uses it without changing the configuration. Multiple roles require selecting the intended player ID and exact region returned by discovery; the provider never guesses between them. Partial input filters discovery, so entering a region alone can select one role in that region. The region is a launcher dictionary key such as `Europe`, **not** the hashed server IDs used by the gacha API.

Optional DPAPI protection uses the current Windows user's versioned UTF-8 credential envelope. A protected-token decode failure stops the refresh; it never falls back to another plaintext credential or user account. Keep tokens private; a token provides access to the account information available to the SDK.

Supported provider settings are `GameToken`, `GameTokenProtected`, `PlayerId`, `Region`, `DeviceId`, `RefreshSeconds` (30–86400, default 300), `TimeoutSeconds` (1–120, default 15), and `MaximumBytes` (1024–16777216, default 1048576). `UID` and `Server` are validation aliases. The host's per-tile model supplies its own section/key prefix; see the tile's settings or exported INI for the exact persisted path. A blank device ID creates one UUID for the complete refresh flow. An explicit device ID is reused across refreshes.

## Data displayed

The provider reads the upstream `Base` model's waveplates and maximum, recovery timestamp, refined waveplates and maximum, daily activity/unlock state, and weekly challenge attempts remaining. It displays only fields returned by the service. Missing recovery data is shown as unavailable, and missing optional counters are omitted. It does not invent a weekly maximum or infer a reset schedule. The returned player ID must match the selected ID before data is published.

The implementation follows [the current launcher query flow](https://github.com/Wuthery/kuro.py/blob/4be620b2fbdc05eb2e2b6bb3aba68ae348d27c22/kuro/client/components/game.py) and [role field definitions](https://github.com/Wuthery/kuro.py/blob/4be620b2fbdc05eb2e2b6bb3aba68ae348d27c22/kuro/models/game.py). Although the reference project declares a PGR game enum, its inspected role/energy endpoints and account setup are WuWa-specific. **Punishing: Gray Raven, Chinese-region WuWa, and other Kuro games are not advertised as supported.**

## Runtime and validation

October 26 adds configurable last-success age, retained-data presentation and independent tile/popup failure thresholds. See [the current source-health guide](wuwa-source-health-2026-10-26.md). Its completed-attempt policy supersedes the earlier fixed two-transient-failure notice threshold; inner HTTP retries remain part of one source attempt.

Each demanded tile owns an asynchronous provider. An unconfigured or unpinned tile starts no Kuro network activity. A configuration change cancels the old request, and results from another account/role revision cannot replace the current result. Refreshes use fixed HTTPS hosts, POST bodies, a bounded response size, one deadline shared by OAuth/discovery/query, and cancellation. Automatic redirects are disabled so credentials cannot be forwarded to a redirected host. Launcher status `1005` gets one initial attempt plus at most three retries, matching the reference client's `max_attempts=3` recursion. Short cancelable pauses of 250, 500 and 1000 milliseconds avoid consuming every attempt in one immediate burst; they never extend the request's overall deadline.

The portable model and native adapter tests inject synthetic responses and cover role mismatch, discovery ambiguity, malformed/duplicate JSON, unsafe account fields, Unix/ISO recovery timestamps, redacted failures, optional credential decoding, provider caching/cancellation, and empty-credential inactivity. Shared HTTP tests use isolated loopback listeners to check POST body integrity, disabled redirects, finite waits, and final callback/body release. They never connect to Kuro's service. Successful mocked protocol tests do not establish that a real account token or server will be accepted.

The separate `KuroAuthTests` fixture covers the password transformation and signing reference vectors, both SDK request shapes, human-verification status/proof parsing, nonce rejection, cancellation, redirects/HTTP errors, credential-redacted failures, retained-token character retry, and compact/expanded dialog geometry. It never signs into an account. The actual Kuro acceptance and human challenge remain user-driven acceptance checks after the native application is built and installed.
